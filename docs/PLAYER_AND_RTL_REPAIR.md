## B. Root causes and fixes

### B1 — the player was created twice (P0-2, shipped defect)

**Evidence.** `PlayerFactory.cs:63-70` (before) added `PlayerMotor`, `PlayerCombat`, `PlayerHealth`,
`PlayerInputReader`, `GameplayInputRouter`, `PlayerController` in that order, and `PlayerCombat.cs:26`
and `PlayerHealth.cs:24` each carried `[RequireComponent(typeof(PlayerController))]` while
`PlayerController.cs:56-58` requires both of them back.

**Mechanism.** Unity satisfies `[RequireComponent]` by *adding* the missing component to the object,
and it does so when the component is added — an inactive object does not change that. So adding
`PlayerCombat` added a `PlayerController` of its own, and the explicit `AddComponent<PlayerController>()`
two lines later added a second one. `controller.Configure(tuning)` configures only the second, and
both awaken when the object is switched on. This is not a test-only path: no scene and no resource
references the player components' GUIDs, so `PlayerFactory.Create` is the only way a player is built,
in the game and in the tests alike.

**Fix.** The dependency now points one way, which is how the enemy pipeline was already built
(`EnemyHealth.cs:30` requires only the motor; `EnemyFactory.cs:58-60` adds motor, health, controller):
the controller requires its parts, the parts look the controller up and every use is null-checked. The
parts are added in the order that satisfies the controller's requirements with exactly the components
the factory creates, each is `[DisallowMultipleComponent]`, and `PlayerFactory.RequireSingle<T>`
asserts the result instead of assuming it.

### B2 — a controller without tuning threw once per physics step (P0-1)

**Evidence.** CI run `38643895478`, job `116126358545`: `tests total=26 passed=2 failed=24`,
`frames written=0`, and the annotations carry
`NullReferenceException … Aether.Gameplay.Player.PlayerController.FixedUpdate () (at Assets/Aether/Code/Aether.Gameplay/Runtime/Player/PlayerController.cs:198)`
with `UnityEngine.Debug:LogError (object,UnityEngine.Object)` — the two-argument error from the old
`Awake` — in `playmode.log`. At `2efef1a`, line 198 dereferenced `_tuning.CoyoteTime` and `Awake` only
logged the missing asset, so the untuned controller threw on every physics step, the state machine
never ticked, and the exception surfaced as an unhandled log message in the `SetUp`/`TearDown` of
unrelated tests.

**Fix.** `ValidateTuning` runs at the end of `Awake`: without a tuning asset the controller logs one
error naming the fix, sets `enabled = false`, and `Update`, `FixedUpdate` and `OnEnable` return early
on `!IsInitialized`, so a re-enabled controller cannot reach a movement step either. `PlayerFactory`
reports the separate case where a tuning asset was supplied but did not reach the controller. The
motor, health and combat degrade on their own (`PlayerMotor.ApplyGravity` and friends already
return on a null tuning), and the only other place the tuning is dereferenced — the dodge and the
hurt/dead states — is reachable only through the guarded movement loop.

`ae93c82747fb1bd9970c94e525e79350`. A scan of all 233 GUIDs under `Assets/` found no collision.

### B4 — the gate that proves the gates work had gone stale (P0-4, fixed in `27d218d`)

**Evidence.** `negative_controls.py` aborted on the first control that could no longer find its
pattern, reporting one stale control. Injecting every control's mutation separately showed **five**:
`SecondaryPitch`, the Collection row, `menu.title` in the Spanish sheet, the `CreateTrackedText`
argument order, and the `_system`/Credits row.

**Fix.** All five re-pointed at current source; the pitch control now retunes by constant *name* like
the other seventeen, so it cannot go stale from a value change again. The suite reports
`99/99 injected faults detected`.

### B5 — lam followed by alef was drawn as two letters (P1-5)

**Evidence.** `RtlText.ShapeRun` had no ligature: for `لام`-shaped input it emitted the lam's medial
or initial form next to the alef's final form, which leaves the lam's connector running into the
alef's stroke. Eight pairs exist in the Persian sheet, including `سلامتی`
(`pause.restart.body`, `strings_fa.txt:265`) and `علامتی` (`character.precursor.body`, line 211);
Persian is the shipped default language, and the UI uses Unity's legacy `Text` component, which runs
neither the bidi algorithm nor the font's OpenType shaping.

**Fix.** `Lam` followed by an alef variant is resolved before the per-letter table, with the four
precomposed families (`0xFEFB`/`0xFEFC` plain, `0xFEF5`-`0xFEFA` for madda and the two hamzas) and the
isolated or final form chosen by whether the letter before the lam joins forward, exactly as a lone
lam would. Marks written between the two letters stay attached to the ligature. Everything else is
untouched, and the two strings that matter were checked by hand: `سلامتی` now shapes as
`FBFD FE98 FEE3 FEFC FEB3` and `علامتی` as `FBFD FE98 FEE3 FEFC FECB`.

**Glyph coverage was checked before the change was made**, because a ligature the font lacks renders
as a box: the bundled `Vazirmatn-Regular.ttf` maps `U+FEF5`-`U+FEFC` (glyph ids 1295-1302 of 1333) and
the Persian yeh forms the existing code already uses. `fontTools` was the authority; a hand-written
cmap reader written first disagreed with it on some code points and was discarded.

### B6 — damage dereferenced the controller it no longer requires (part of B1)

`PlayerHealth.TakeDamage` called `_controller.EnterHurt(...)` unguarded, so removing the requirement
without touching that line would have turned a wiring mistake into an exception inside damage
handling. The hit reaction is now skipped when there is no controller; the damage, the knockback and
the death event are unaffected.

### B7 — a verifier false positive (tooling, not game code)

`tools/verify/mainmenu.py` read a member's names from its body alone, so an `out` parameter assigned
inside the body was reported as an unknown name, and because its declaration scan needs a separator in
front of each name it was missing most parameters of any signature. The check now reads parameters
from the declaration's own parentheses. This is a stricter reading of the source, not a weaker check:
all 99 injected faults are still detected, including the two scope controls
(`SaveSlotScreen.cs:122 assigns to 'note'` and `:111 passes 'DepartToMenu'`).

## F. Safe next steps toward a verified APK

1. **Run the PlayMode suite first, with no release involved.** `intro-render.yml` is the only workflow
   that runs `game-ci test --testPlatforms=playmode`; it needs `contents: read`, uploads frames and
   results, and publishes no release. Its `push` trigger does not list this branch, so it must be
   dispatched by hand on this branch (`workflow_dispatch`, choosing the branch). It needs the
   `UNITY_EMAIL` and `UNITY_PASSWORD` secrets, and its own annotations are the way to read the result
   from here, since the runner's artifacts and logs live on storage this environment cannot reach.
   **Nothing was dispatched during this work.**
2. **Do not push to `release/aether-latest-build-retry` and do not dispatch `android-build.yml` as it
   stands.** Its `release` job has `contents: write` and, whenever the build succeeds, publishes a
   non-draft GitHub release with the APK. There is no build-without-release input today.
3. **To get an APK without publishing anything**, change the pipeline first, in its own review:
   give the release job a guard — for example a `workflow_dispatch` input such as
   `publish: false` in the job's `if:` — or move the release job into a separate workflow that only
   runs on the release branch. Then the `apk` job can be dispatched on a reviewed commit and its
   artifact downloaded by the owner. Doing this outside CI (a machine with Unity 6000.3.24f1 and
   Android build support) achieves the same thing without touching the repository's release path.
4. **Read the result as evidence, not as a green light.** A verified repair looks like: the dispatched
   run reports 36/36 PlayMode tests, the gameplay render test writes its frame and summary, and the
   APK's sha256 is recorded next to the commit it was built from.
5. Only after that: the documentation drift in section D as a separate change, and the owner's
   decisions about application identity, company name and versioning, which this repair deliberately
   did not touch.
